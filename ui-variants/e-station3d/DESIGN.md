# 案 E「駅の立体図」 DESIGN.md（e-station3d）

**結論**：案 D「計器」VFX（`ui-variants/d-instrument-vfx/`）をそのまま写し、動き（ばねの基盤 `js/motion.js`・`js/vfx.js`）には手を入れずに、次の 4 つを足した。元のフォルダは変更していない。
1. **始発・終電**：時刻の 3 択の右隣に、小さなアイコン付きのボタン 2 つ（始発・終電）。
2. **極細のスクロールの棒**：標準の棒を消し、つまみだけ（見た目 3px）。当たり判定は左右 28px・上下 10px 広い。ドラッグでスクロールできる。
3. **アイコン中心**：タブはアイコンだけ（名前は aria-label）。新しいボタンもアイコン＋aria-label。
4. **駅の立体図**：枠線だけの 3D の駅（ダークは黒い面に白く光る線、ライトは紙の面にインクの線）（架空の見本）。最短の乗換の道を青緑に光る線でたどり、号車・ドアを指定でき、いちばん早いドアを提案する。

デザインの土台（色・書体・余白・動きの表）は案 D と同じ：`ui-variants/d-instrument-vfx/DESIGN.md`。

## 要約（非エンジニア向け）
1. 検索画面のいちばん上に「始発」「終電」のボタンがあります。出発地と目的地を入れて押すと、すぐに検索します。

3. 下のタブは文字をやめてアイコンだけにしました（読み上げでは名前が読まれます）。
4. 新しい「駅の立体図」タブ（立方体のアイコン）で、大きな駅の中を立体で見られます。指で回し、2 本指で拡大します。
5. 「乗るホーム」「号車」「ドア」「乗換先」を選ぶと、乗換の道が光る線で描かれ、歩く時間が出ます。

9. 駅は**架空の見本**です。実在の駅の構造や号車・ドアの位置ではありません。
10. 実在の駅で使うには、駅の中の地図と号車・ドアの位置のデータが要ります。手に入るかは、まだはっきりしません（下の「データの現実」）。

## 2. スクロールの棒
| 項目 | 値 |
|---|---|
| 標準の棒 | 消す（`scrollbar-width: none`・`::-webkit-scrollbar`）。キーボード・ホイール・指のスクロールは標準のまま |
| 見た目 | つまみだけ。幅 3px・角丸・文字の弱い色で不透明度 .55。掴む／マウスを乗せると幅 5px・青緑 |

## 3. 駅の立体図
### 見た目：GNOTO の 3D 音響スタジオの線画を参考にした
`/home/user/GLYPH/addons/mstudio-hallview.js`（音楽スタジオの「ホールの響き」の 3D 表示）を grep で調べた。手法は次のとおり。
- 面は描かず、**線分だけを白一色**で描く（`LineSegments`、色 `0xffffff`）。背景はほぼ黒 `#020306`。
- **足し算の合成**（`AdditiveBlending`）。線が重なる所ほど明るい。
- **奥行きで薄くする**：線の不透明度 ×（1 − 0.74 × smoothstep(near, far, 奥行き)）。
- **光のにじみ**：`UnrealBloomPass`（強さ .42・半径 .38・しきい値 .04）。

この試作は「外部のライブラリ・CDN を使わない」約束なので、three.js は使わず Canvas 2D で同じことをした：
- 足し算の合成＝`globalCompositeOperation = "lighter"`、奥行きの薄れ＝同じ式（係数 0.74）。
- にじみ＝同じ線を 3 回重ねる（幅 5px・強さ 9%／幅 2.2px・22%／幅 1px・95%）。本物のぼかしより安い近似。
- 線は不透明度を 12 段に丸めてまとめて描く（1 フレームの線の描き込みは数十回）。
- 立体図の面はテーマに従う（ダークは黒い面に足し算の光、ライトは紙の面にインクの線・にじみなし）。

### 何を描くか
| もの | 形 |
|---|---|
| 階 | 床の枠＋天井の淡い枠＋四隅の柱（コンコースは高さ 3.2m、ホームは 1.1m の台） |
| 線路 | 2 本のレール（淡い線） |
| 号車の区切り | ホームの縁の短い縦線 |
| 階段 | 両側の段々の線（9 段） |
| エスカレーター | 斜めの 2 本＋手すり |
| エレベーター | 縦の箱（下の階から上の階の少し上まで） |
| 改札 | 通路を横切る低い柱の列 |
| 出口 | 門の枠 |
| 選んだ号車・ドア | 号車の枠（青緑）・ドアの縦線（琥珀） |
| 経路 | 青緑の光る線（4 重）。始点（ドア）に琥珀の輪、終点に青緑の輪 |

階の名前は、各階の床の板の左端の角の内側に、小さな「1F」「B2F」のタグだけを置く（引き出し線なし・一定の大きさ・重なれば縦にずらす）。強調は下の階ボタンで行い、選んだ階のタグだけ濃く、ほかは薄い。高さは 2.6 倍に誇張（そのままだと 200m の駅に対して 20m の高さが薄すぎる）。「階の間隔を広げる」で 5 倍。

### 操作
| 操作 | 動き |
|---|---|
| 1 本指／マウスのドラッグ | 回転（上下の傾きは 8°〜80°に制限）。離すと慣性で少し回って止まる |
| 2 本指 | つまんで拡大縮小（0.6〜6 倍）＋平行移動 |
| ホイール | 拡大縮小 |
| キー（立体図に焦点） | 矢印＝回転、＋／−＝拡大縮小 |
| 視点を戻す（アイコン） | 最初の視点。全体が収まるよう倍率と中心を合わせ直す |

立体図の領域は `touch-action: none`（指の操作を回転に使う）。ページのスクロールは立体図の下の部分で行う。

### 動き
| 場面 | 長さ | 動きを減らす設定 |
|---|---|---|
| 経路の線が始点から伸びる | 0.9 秒 | 最初から全部出す |
| 進む向きの光の粒が線をなぞる | 1.6 秒 × 2 回だけ（その後は止まる） | 出さない |
| 回転の慣性 | 減衰（毎秒 e^−5.5） | 慣性なし |
| 階の間隔を広げる | 指数で近づく（約 0.4 秒） | 即時 |
| おすすめのドアにした時の数字 | 案 D のばね（release） | なし |

描画は必要な間だけ回す（待機中は止まる）。画面を離れると止める（試験で確認）。

### 経路（最短路）
- グラフ：ノード＝ホームの昇降口・階段／エスカレーター／エレベーターの上と下・通路の点・改札・出口。辺＝歩く秒数（`sec`）と種類（walk・stairs・escalator・elevator・gate）。
- 始点はドア。ドアから同じホームの各昇降口まで「ホームを歩く」辺（距離 ÷ 毎秒 1.0m）を足して、ダイクストラで解く。
- 乗換先がホームなら、その昇降口のどれかに着けば終わり。出口ならその点。
- **不明の扱い**：秒数が不明の辺（`sec: null`）は時間を足さずに「不明の区間の数」を数え、費用を（不明の数, 秒）の辞書順で比べる。不明を通らずに行けるならそちら、通るしかないなら不明の最も少ない道。画面には「3分11秒＋不明 1 区間」のように出し、手順の行にも「不明」と出す。見本ではエレベーター3 の秒数を不明にしてある（段差なしで環線へ行くと必ず通る）。
- **おすすめのドア**：そのホームのすべての号車・ドアで同じ計算をして、いちばん早いものを出す。
- **既存の src/ の再利用**：コアの `src/raptor.ts` は時刻表の RAPTOR で、駅の中のグラフの最短路の関数は無かった（`grep` で確認）。駅の中は小さな（数十ノードの）グラフなので、依存ゼロのダイクストラを `js/station-graph.js` に書いた。コアに入れるなら、RAPTOR の乗換時間（`transfers.txt` の `min_transfer_time`）を、この計算で作った「号車・ドアごとの乗換時間」に置き換える形が考えられる（未実装）。

## 4. データの現実（取れる・取れない）
`docs/research-japan-data.md` には、駅の中の構造と号車・ドア位置のデータは**調べられていない**（時刻表・路線・OSM のライセンスが中心）。以下は、この作業でネットを調べ直していない、手もとの知識による見込み。確からしさを付ける。

| データ | 取れそうか | 確からしさ | メモ |
|---|---|---|---|
| ODPT の駅施設（`odpt:StationFacility`） | 一部の事業者（東京メトロ・都営など）で、エレベーター・エスカレーター・トイレなどの設備と、ホームの「何号車付近に何がある」の情報があるとみられる | 推（未確認） | どの事業者・どの駅に、どこまであるかは不明。ライセンスはデータごとに基本ライセンス（再配布禁止）か CC BY 4.0（research-japan-data.md の注記）。JR 東日本・大手私鉄は「チャレンジ 2026 限定」でしか出ていないものが多く、商用には使えない見込み |
| 号車・ドアの位置（「7 号車 3 番ドアが階段に近い」） | 公的なオープンデータで、全国の駅を網羅したものは知らない | 不明 | ODPT の上の情報が「号車」単位で一部あるかもしれない（推）。**ドア番号**の単位の公開データは見つけていない（不明）。乗換案内の会社は自社で調べたデータを持つが有料・非公開（推） |
| OSM の駅の中（Simple Indoor Tagging：`indoor=*`・`level=*`、`railway=platform`、`highway=steps`・`highway=elevator`・`conveying=*`、出入口） | 形のタグの仕組みはある。日本の大きな駅で、階・通路・階段がつながった形で描かれている駅は少ないとみられる | 推（未確認） | ODbL（帰属表示と、改変データの同じライセンスでの配布）。歩く秒数は無いので、長さから推定するしかない（推の値になる）。号車・ドアのタグは標準が無い（不明） |
| 国の歩行空間ネットワークデータ（国交省・国土地理院の屋内地図・歩行者ネットワーク） | 一部の大きな駅周辺で公開された例があると記憶している | 推（未確認） | 対象の駅・更新の有無・ライセンスは不明 |
| 歩く秒数 | どのデータにも直接は無い見込み | 推 | 長さ ÷ 歩く速さで作る（推の値として表示すべき）。階段・エレベーターの待ち時間は不明 |

**この試作の扱い**：上がはっきりしないため、架空の駅（`data/sample-station.json`、名前は「見本中央（架空）」）で動かした。寸法・秒数・号車とドアの位置はすべて作り物で、実在の駅を表さない。画面にも「架空の駅の見本」と出す。

**次に確かめること**：①ODPT の `odpt:StationFacility` の実データ（どの事業者・駅に、号車の情報がどこまであるか、ライセンス）。②OSM で日本の大きな駅の indoor の描き込みの量（Overpass で `indoor=*` を数える）。③国の歩行空間ネットワークデータの対象駅とライセンス。

## データの形（gyrotraffic-station-v0）
- `levels[]`：`id`・`name`・`z`（m）
- `areas[]`：`level`・`kind`（platform／concourse）・`rect`（[x0, y0, x1, y1] m）
- `tracks[]`：線路（描画だけ）
- `platforms[]`：`axis`（x／y）・`center`・`cars`・`carLen`・`doors`（1 両のドア数）・`car1Front`（1 号車の端の位置）・`dir`（号車が増える向き ±1）・`access`（昇降口のノード）
- `nodes[]`：`level`・`x`・`y`・`kind`（stairs／escalator／elevator／gate／exit／concourse）・`name`
- `edges[]`：`a`・`b`・`sec`（秒。不明は null）・`kind`・`oneway`（省略時は両方向）
- `assumptions.platformWalkMps`：ホーム上の歩く速さ（見本は毎秒 1.0m）
- ドアの番号は 1 号車の側から数える（実際の数え方は事業者ごとに違う見込み：不明）
