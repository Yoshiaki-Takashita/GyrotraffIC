# 経路探索の中核（ルーティングコア）設計　第 1 版・2026-10-19

> 印の意味：**[PROVEN]**＝一次資料か数学的根拠で確認済み。**[ARGUED]**＝根拠を示した推論（反証されうる）。**[GUESS]**＝推測（実測で直す）。**[UNKNOWN]**＝分かっていない。
> 対象：`docs/decisions.md` の決定（自作の RAPTOR 方式、首都圏の地下鉄・私鉄から、運賃は後、OTP は照合用）に沿った、エンジン本体の設計。実装（`src/`）は別セッションが担当するため、本書は「何を・なぜ」を定め、言語や API の細部は縛らない。

## 要約（非エンジニア向け・10 行）
1. 時刻表を「同じ停車順の便の束（パターン）」にまとめ、乗り換え回数を 1 回ずつ増やしながら到着を早める **RAPTOR** 方式で探す。最速と乗り換え最少は同じ 1 回の計算から出る。
2. 飛行機は別の仕組みにせず、**同じエンジンに「乗る前の余裕」「降りた後の余裕」を足した便として入れる**。余裕は国内・国際、預け荷物の有無で変える。
3. 答えは 1 本でなく、最速・乗り換え最少・（運賃が全部分かる時だけ）安い、の複数案。運賃が一部でも不明なら「運賃不明」と正直に出し、安い順には入れない。
4. 深夜（24 時過ぎ）の便、平日・土休日・祝日・年末年始のダイヤは「運行日（サービス日）」で扱い、前日のダイヤの便も取り込んで探す。
5. 直通運転は「座ったまま乗り換え 0 回」として扱う。1 対 1 の直通は取り込み時に 1 本につなぐ。分割・併結は別扱い。
6. 日本のデータは同じ駅が事業者ごとに別の ID で出てくる。物理の乗り場は別のまま残し、「駅の束」でまとめて、束の中の歩行時間を乗り換え時間にする。
7. 出入口・構内通路・駅間の徒歩は別の「徒歩グラフ」で持ち、精度の出どころを各点に記録する（`platform-precision.md`）。
8. 壊れたデータは取り込み時に検査して隔離し、前の版に戻せる。探索時にも「待ち時間が負」などの矛盾を出さない守りを入れる。
9. 正しさは、①OpenTripPlanner と同じデータで答えを突き合わせる、②人手で確かめた「正解の経路」、③「出発を遅らせたら到着も遅くならない」等の性質テスト、の 3 本で確かめる。
10. 規模の見込み：首都圏の地下鉄・私鉄なら 1 回の探索は 10 ミリ秒級、メモリは数十 MB [GUESS]。全国でも数 GB に収まる [GUESS]。段階 1 で実測して直す。

## 1. 目的と範囲

- 目的：出発地・目的地・時刻（出発後／到着前）を受け取り、鉄道・バス・フェリー・飛行機を組み合わせた **複数の良い経路（パレート集合）** を返す。
- 範囲内：時刻表探索、徒歩の接続、飛行機の余裕時間、運行日（カレンダー）、直通運転、データ不良への耐性、検証計画、計算量。
- 範囲外（別文書）：データの取り込み手順とライセンス（`data-pipeline.md`）、乗り場位置の精度（`platform-precision.md`）、アカウント（`accounts-privacy.md`）、段階計画（`roadmap.md`）。
- 範囲外（将来）：遅延・運休のリアルタイム反映、自転車・車との組み合わせ、予約・空席。

## 3. データモデル（エンジンの入力）

GTFS（静的）の語彙をそのまま使い、足りない所だけ拡張する。GTFS の `stops.txt` は `location_type` で「乗り場（0）・駅（1）・出入口（2）・構内ノード（3）・乗車位置（4）」を区別でき、`pathways.txt`・`levels.txt` で構内通路と階を表せる [PROVEN：GTFS Schedule Reference、本文中の値は gtfs.org の仕様に基づく。`review-architecture.md` の検証表を参照]。

### 3.1 要素の一覧

| 要素 | 相当する GTFS | 中身 | 拡張・注意 |
|---|---|---|---|
| **Operator** | `agency.txt` | 事業者名・タイムゾーン・言語 | ライセンスと出典表示の文言を持つ（P4） |
| **Station（駅・空港・港の束）** | `stops.txt` location_type=1 | 名前（多言語）・代表位置・国・タイムゾーン・種別（鉄道／バス／港／空港） | 自前の安定 ID。複数データ源の駅をまとめる「束」（3.4） |
| **StopPoint（乗り場）** | location_type=0（＋4） | ホーム番線・バス停の標柱・桟橋・空港ターミナルの位置・向き・階 | **バス停は進行方向ごとに別の点**。位置の精度と出どころを持つ |
| **Entrance（出入口）** | location_type=2 | 出入口番号・位置・階・段差の有無 | 街路の徒歩はここに接続する |
| **Node / Pathway（構内通路）** | location_type=3、`pathways.txt` | 出入口↔乗り場、乗り場↔乗り場の歩行時間、階段・エレベーター等の種別 | 無ければ距離から推定し「推定」と印を付ける |
| **Line（路線）** | `routes.txt` | 名前・種別・色・事業者 | 表示用。探索は Pattern を使う |
| **Pattern（停車パターン）** | （GTFS に無い。前処理で作る） | 同じ停車順（StopPoint の列）を持つ便の束 | RAPTOR の「route」に相当 [PROVEN：Delling らの定義。付録 A] |
| **Trip（便）** | `trips.txt` | Pattern・運行日 ID・方向・列車番号・車両の情報（車椅子可など） | 飛行機の便もここ（`mode=air`）。`block`／直通の連結情報（5 章） |
| **StopTime（停車時刻）** | `stop_times.txt` | 到着・出発の秒（運行日の 0 時からの秒。24 時を超えてよい） | 乗降の可否（`pickup_type`／`drop_off_type`） |
| **Service（運行日）** | `calendar.txt`＋`calendar_dates.txt` | 曜日パターン＋例外日 | 日本の祝日・年末年始は取り込み時に **具体的な日付に展開** して持つ（6 章） |
| **Transfer（乗り換え規則）** | `transfers.txt` | 乗り場間の最小乗換時間、便間の「座ったまま」接続 | 直通運転は便間接続（5 章） |
| **Footpath（徒歩）** | （`transfers.txt` type 2 ＋自前） | StopPoint 間、Entrance↔StopPoint 間の歩行秒と距離、段差の有無 | 街路（OSM）から前処理で計算。推定なら印を付ける |
| **FareProduct / FareLegRule** | GTFS Fares v2 | 運賃の規則（後の段階） | 無い区間は「不明」。4.3 |
| **AirBuffer（空港の余裕）** | （拡張） | 空港・航空会社・国内／国際・荷物の有無ごとの、乗る前の余裕・降りた後の余裕・最小乗継時間 | 7 章 |
| **Provenance（来歴）** | （拡張） | 各レコードの データ源 ID・版・取得日時・ライセンス ID | `data-pipeline.md` |

### 3.2 ID と版

- 内部 ID は `源:元ID` の形（例 `odpt:odpt.Station:TokyoMetro.Ginza.Shibuya`、`gtfsjp.<feed>:stop_123`）。元 ID を失わない [ARGUED：元に戻れる ID でないと来歴（P4）と差分テストが成り立たない]。
- 「駅の束」には自前の安定 ID（`gy:station:...`）を振り、元 ID の集合を持つ。束の作り方は 3.4。
- 時刻表全体に **版（スナップショット ID）** を付け、探索結果は「どの版で計算したか」を返す。版は取り込み（`data-pipeline.md`）が付ける。

### 3.3 時刻の表し方

- 内部：`運行日（ローカル日付）` ＋ `その日の正午 − 12 時間 からの秒`（GTFS の慣例。夏時間のある国でも破綻しない）[PROVEN：GTFS 仕様の `arrival_time` の定義。日本には夏時間が無いので実務上は「0 時からの秒」と同じ]。
- 探索は「運行日の秒」で行い、入出力の瞬間（絶対時刻）との変換は駅のタイムゾーンで行う。国内線だけなら日本標準時 1 つだが、国際線・海外（段階 5）で必要になるため最初から駅ごとにタイムゾーンを持つ [ARGUED：後から足すと全データの作り直しになる]。
- 24 時を超える時刻（例 `25:10:00`）は前日の運行日の便として持つ（6 章）。

### 3.4 日本の「同じ駅が何度も出てくる」問題と駅の束

- 事象：ODPT の駅 ID は **事業者 × 路線 × 駅** の単位で、渋谷は銀座線・半蔵門線・東横線…で別の ID になる [ARGUED：ODPT の ID 体系 `odpt.Station:<事業者>.<路線>.<駅>` の形から。実データは登録完了後に確認]。ODPT の `odpt:Station` には「乗り換え可能路線（`odpt:connectingRailway`）」「乗り換え可能駅（`odpt:connectingStation`）」の属性があり、これが束の根拠①になる [ARGUED：有志が ODPT 仕様を写した OpenAPI 定義（https://github.com/sophie-app/odpt-openapi `src/models/train.tsp`）で確認。公式仕様は登録後に照合]。GTFS-JP のバス停は標柱（乗り場）ごとに 1 行で、親停留所が無い場合がある [UNKNOWN：フィードごとに差がある。取り込み時に統計を取る]。
- 方針：
  1. **物理の乗り場（StopPoint）は決して統合しない。** 統合すると「どの番線か」の情報が消える。
  2. 「駅の束（Station）」を作る。束の根拠は、強い順に、①データ源が示す接続情報（GTFS の `parent_station`、ODPT の接続駅の属性 [UNKNOWN：属性名はデータ入手後に確認]）、②同じ事業者内の同名駅、③距離（例 鉄道 200 m・バス 100 m 以内 [GUESS]）＋名前の正規化一致（「駅」「前」の有無、全角半角、読み）、④人手の対応表（主要駅）。
  3. 束の中の乗り換え時間は、構内通路（Pathway）があればそれを、無ければ距離と駅の規模からの推定値に印を付けて使う（4.5）。
  4. 束の **根拠と確信度** をレコードに残す（人手＞データ源＞同名＞距離）。差分テストで、束の違いによる答えの違いを見つけられるようにする。

## 4. 探索アルゴリズム

### 4.1 なぜ RAPTOR か（決定の再確認）

- RAPTOR（Round-bAsed Public Transit Optimized Router）は、乗り換え回数 k を 1 ずつ増やす「ラウンド」を回し、各ラウンドで前ラウンドに改善のあった停留所を通る **パターンを 1 回ずつ走査** する。優先度付きキューを使わず、配列の走査だけで動く [PROVEN：Delling, Pajor, Werneck, "Round-Based Public Transit Routing", Transportation Science 49(3), 2015（ALENEX 2012 の拡張）。付録 A]。
- 到着時刻と乗り換え回数の 2 基準のパレート集合が **そのまま** 出る（ラウンド k の最良到着＝「乗り換え k 回以下の最速」）。これが「最速」「乗り換え最少」を 1 回の計算で出せる理由 [PROVEN：同論文]。
- 同じ論文に、出発時刻の幅を一度に解く rRAPTOR と、3 基準以上を扱う McRAPTOR がある [PROVEN：同論文]。
- 代案との比較：時間展開グラフ上の Dijkstra は実装が簡単だが、基準を増やすと遅く、時刻表の更新時にグラフを作り直す。CSA（Connection Scan）は最速 1 基準では速いが乗り換え回数の扱いが素直でない。Transfer Patterns 等は前処理が重く、データ更新が週次の本件では割に合わない [ARGUED：いずれも文献上の性質。本件はデータが小さく、RAPTOR の単純さが利点]。

### 4.2 前処理（時刻表の版ごとに 1 回）

1. **Pattern 化**：各 Trip の StopPoint 列をキーに Trip を束ね、Pattern を作る。Pattern 内の Trip は **最初の停留所の出発時刻で並べ、追い越しが無いこと（FIFO）を検査** する。追い越しがあれば別 Pattern に分ける [PROVEN：RAPTOR の正しさは「パターン内で後の便が前の便を追い越さない」ことに依存する（同論文）]。
2. **索引**：StopPoint → それを通る (Pattern, 位置) の一覧。Pattern → StopPoint 列と Trip の時刻表（到着・出発を連続配列に）。
3. **徒歩（Footpath）集合**：StopPoint 間の歩行秒。**推移閉包**（a→b、b→c があれば a→c も入れる）を取るか、上限（例 15 分 [GUESS]）で打ち切る。RAPTOR は「1 ラウンドに徒歩 1 本」を仮定するため、閉包を取らないと最適解を取りこぼす [PROVEN：同論文の前提]。閉包が膨らむ大規模駅群（新宿・渋谷周辺）は上限で抑え、取りこぼしの有無を差分テストで監視する。
4. **運行日の展開**：Service を日付ごとの「有効な Trip の集合」に展開し、ビット列で持つ（1 年分×Trip 数のビット。首都圏で数 MB [GUESS]）。
5. **直通の連結**（5 章）と **空港の余裕**（7 章）の前処理。
6. 以上を不変（immutable）のスナップショットとして固め、探索中は書き換えない（P5、同時に複数の問いを処理できる）。

### 4.3 問い（クエリ）と答え

**入力**
- 出発・目的：座標（街路で乗り場に接続）か、Station／StopPoint の ID。
- 時刻：「この時刻以降に出発」か「この時刻までに到着」。幅（例 出発 8:00〜9:00）も可。
- 条件：使わない手段、最大徒歩、段差なし、飛行機の国内／国際と預け荷物、最大乗り換え回数（既定 例 5 [GUESS]）。

**出力**：経路（Journey）の集合。各経路は区間（Leg）の列。各 Leg は 乗車（Trip の区間）／徒歩（Footpath・Pathway）／待ち（空港の余裕を含む）。各 Journey に基準値（到着時刻・出発時刻・乗り換え回数・徒歩距離・運賃〈4.4〉）と来歴の参照、計算に使った時刻表の版。

**基準と選び方**
| 案 | 定義 | 出し方 |
|---|---|---|
| 最速 | 到着が最も早い | パレート集合の最小到着 |
| 乗り換え最少 | 乗り換え回数が最小。同数なら到着が早い | 各ラウンドの最良のうち回数最小 |
| 安い | 運賃合計が最小。**運賃が全区間で分かる経路だけ** | 4.4 |
| （後で）歩き少なめ、出発が遅い（最遅出発）、座席確保しやすい | — | McRAPTOR か後処理 |

- 「出発が遅い」案は、「この時刻までに到着」の問いの自然な答え。逆向き探索（時刻表を反転した RAPTOR）で出す [ARGUED：RAPTOR は対称なので時刻と向きを反転すれば同じコードで動く]。
- 表示用の間引き：到着が 2 分しか早くないのに乗り換えが 1 回多い経路は表示から外す等の「緩い支配」は **表示層** で行い、エンジンは厳密なパレート集合を返す（P2）。

### 4.4 運賃：「不明」を値として持つ

運賃は当面「あれば目安」[PROVEN：`decisions.md` 3]。エンジンでは次の形にする。

- Leg ごとの運賃は 3 値：`Known(金額, 通貨, 根拠)` ／ `Partial(下限, 不明な要素)` ／ `Unknown(理由)`。
- Journey の運賃＝全 Leg の合成：すべて Known なら Known（通算規則があれば適用）、1 つでも Unknown なら Unknown、Partial を含めば Partial（下限の合計）。
- 「安い」案：**Known の Journey の中だけ** で最小。Partial・Unknown は順位に入れず「運賃不明（○○の区間）」と表示する [PROVEN：`decisions.md`「運賃を最初から必須にした場合」の代案そのもの]。
- 目安であることを必ず表示する（IC・切符の差、乗継割引、特急料金の有無を「含まない」と明記）。
- McRAPTOR で運賃を 3 つ目の基準にする時は、Unknown を「最大値」でなく **比較不能** として扱う（Known と Unknown は互いに支配しない）。そうしないと Unknown の経路が全部消える [ARGUED]。

### 4.5 乗り換え時間と徒歩

- 乗り換えの種類と時間：
  1. 同じ StopPoint（同一ホーム対面・同じ乗り場）：最小 0〜1 分 [GUESS]。
  2. 同じ Station 内の別 StopPoint：Pathway があればその歩行秒。無ければ `距離 ÷ 歩行速度（例 1.0 m/s [GUESS]）＋ 階段・改札の固定加算（例 2 分 [GUESS]）`、推定の印付き。
  3. 別 Station：Footpath（街路の歩行秒）。
  4. 便指定の規則（`transfers.txt` の from/to trip）：直通（5 章）。
- 歩行速度・段差なし条件は問いごとに変えられる（高齢者・車椅子）。
- 出発地・目的地から乗り場への接続：街路グラフ（OSM）で半径（例 1 km [GUESS]）内の Entrance／StopPoint を多点 Dijkstra で求め、出入口→乗り場は Pathway で足す。街路探索はエンジン本体から **切り離した部品**（`decisions.md` 1：「街路の経路は別の軽い部品」）とし、無い時は直線距離 × 係数（例 1.3 [GUESS]）で代用し「推定」の印を付ける。

## 5. 直通運転・分割併結・重複した乗り場

### 5.1 直通運転（through service）

- 事象：東京の地下鉄は私鉄・JR と相互直通し、1 本の列車が複数事業者の複数路線を走る。データ上は、事業者・路線ごとに別の Trip に切られ、前後の Trip への参照で結ばれる形が多い [ARGUED：ODPT の `odpt:TrainTimetable` には「直前の列車時刻表（`odpt:previousTrainTimetable`）」「直後の列車時刻表（`odpt:nextTrainTimetable`）」の **ID のリスト** がある（出どころは 3.4 と同じ有志の OpenAPI 定義）。リストなので 1 対多（分割・併結）も表せる。どの事業者がどこまで埋めているかは実データで確認 [UNKNOWN]]。GTFS では `transfers.txt` の `transfer_type=4/5`（座ったまま／降りて同じ車両に再乗車）で便同士を結べる [PROVEN：GTFS 仕様。検証表を参照]。
- 方針：
  1. **1 対 1 の連結**（A の終点＝B の始点、同じ停留所、A の到着≦B の出発）は前処理で **1 本の論理 Trip に連結** する。停車列は連結し、Pattern も連結後の列で作る。表示では事業者・路線の切れ目を Leg の中の「区切り」として出す（乗り換え回数は増やさない）。
  2. **1 対多・多対 1（分割・併結）** は連結せず、便間の「乗り換え 0 回・時間 0」の特別な Transfer として扱う。RAPTOR では「降りて同じ停留所で別の便に乗る」をラウンド内で許す必要があるため、ラウンドの中で「便間接続」を先に適用してから通常の乗り換えに進む [ARGUED：ラウンド数＝乗り換え回数の意味を保つための拡張。差分テストで OTP の interlining と比較する]。
  3. 連結の根拠（データ源の参照／名前と時刻の一致による推定）をレコードに残す。推定の連結は既定で **使わない**（誤った直通は「乗り換え不要」という誤情報になる）[ARGUED]。
- 直通先で種別が変わる（急行→各停）場合も、Trip は 1 本、種別は区間ごとの属性にする。

### 5.2 重複した乗り場（duplicated platforms）

- 事象：同じ物理ホームが、路線ごと・方向ごと・データ源ごとに別の StopPoint として出てくる（例 直通先の路線が同じホームを別 ID で持つ、GTFS-JP で同じ標柱が複数フィードに出る）[ARGUED：3.4 と同じ根拠]。
- 方針：物理的に同一と **確信できる** 場合（同じデータ源内で位置・名前・番線が一致、または事業者の対応表）だけ「同一乗り場」の等価関係を張り、乗り換え時間を 0〜1 分にする。確信できない場合は別の StopPoint として残し、距離からの推定時間で結ぶ。等価関係にも根拠と確信度を付ける。
- 「同一視しすぎ」の危険（別ホームなのに 0 分）の方が「別のまま」の危険（実際は同じホームなのに 3 分見積もる）より大きいので、**疑わしきは別** とする [ARGUED]。

## 6. 時間依存の辺と運行日（サービスカレンダー）

- 乗車の辺は本質的に時間依存（次の便を待つ）。徒歩・構内通路は当面「時間によらず一定」とする。駅の出入口の開閉時刻・終電後の通路閉鎖は、データがあれば Pathway に有効時間帯を持てるようにしておくが、段階 1 では使わない [GUESS：ODPT・GTFS-JP にその情報があるかは未確認 [UNKNOWN]]。
- **運行日の判定**：問いの時刻 t（ローカル）に対し、運行日 D（t の属する日）だけでなく、**D−1 の便（時刻 ≧ 24:00 のもの）と D＋1 の便** も候補に入れる。実装は「D−1 の時刻表に +86400 秒、D＋1 に −86400 秒… ではなく、D−1 を −86400、D＋1 を +86400 でずらして同じ秒軸に重ねる」。これで 0 時台の終電・始発、24 時間運行のバス、翌日に跨る長距離便（夜行バス・フェリー・深夜便）を自然に扱える [ARGUED：GTFS の 24 時超え表記の前提から必然。OTP も同種の処理をしている [UNKNOWN：OTP の実装の細部は未確認]]。
- **祝日・特別ダイヤ**：日本の時刻表は「平日／土休日」の 2〜3 区分で出ることが多く、祝日の扱いは **データ側が明示している場合とそうでない場合がある** [UNKNOWN：フィードごとに確認]。取り込み時に、①`calendar_dates.txt` の明示があればそれを最優先、②「土休日」区分で祝日が未展開なら、内閣府の「国民の祝日」CSV [ARGUED：内閣府が CSV を公開していると理解している。URL は `data-pipeline.md` で確認する] で展開し、展開した事実を来歴に残す。年末年始・お盆の特別ダイヤは、データが無ければ **「通常ダイヤで計算（特別ダイヤ未反映）」と表示** する（P3）。
- **頻度表記（`frequencies.txt`）** は取り込み時に個別の Trip に展開する（RAPTOR は個別便を前提）[PROVEN：RAPTOR の定義]。`exact_times=0`（目安の間隔）の便は「目安」の印を付ける。
- タイムゾーンまたぎ（段階 5）：各 StopTime は「便の運行日 × 事業者のタイムゾーン」で秒を持ち、異なるタイムゾーンの便を接続する時だけ絶対時刻に変換して比較する。国際線は出発空港と到着空港で日付が変わりうるので、Trip 単位で「出発地の運行日」を基準にする [ARGUED]。

## 7. 飛行機と地上交通の結合

### 7.1 方針：同じエンジンに「余裕つきの便」として入れる

`architecture.md` 2.2 は「地上探索 → 便の総当たり → 地上探索」の 2 段方式だった。本書は **同じ RAPTOR に飛行機の便を Trip として入れ、空港の乗り場に「乗る前の余裕」「降りた後の余裕」を持たせる** 方式を第一候補にする。

- 理由 [ARGUED]：
  1. 2 段方式は「空港候補を 2〜3 港に絞る」段階で最適解を落としうる（例 成田に行く方が早いのに羽田に絞る）。同じエンジンならパレート集合の中で地上案と飛行機案が自然に競う。
  2. 空港は **駅の束の 1 種**（鉄道駅・バス停・ターミナルが束になる）なので、別扱いにする理由が薄い。
  3. 実装が 1 本で済み、差分テストの対象が増えない。
  4. 2 段方式は、地域ごとにエンジンを分ける段階 5（海外）で「エンジン間を飛行機層でつなぐ」形として **再登場** する。今はその必要が無い。
- 仕組み：RAPTOR で便に乗る条件を `到着ラベル(p) + 乗る前の余裕(p, 便) ≦ 便の出発(p)` に、降りた時のラベルを `便の到着(p) + 降りた後の余裕(p, 便)` にする。鉄道・バスでは余裕が 0 なので通常の RAPTOR と一致する。パターン内の FIFO 性は保たれる（余裕は便によらず停留所と条件で決まるため）[ARGUED]。
- 空港内の乗り継ぎ（飛行機→飛行機）は、最小乗継時間（MCT）を空港ごと・国内／国際の組み合わせごとに持ち、「同じ StopPoint での乗り換え時間」として適用する。

### 7.2 余裕時間の既定値（すべて設定で上書き可）

| 場面 | 既定値 | 根拠 |
|---|---|---|
| 国内線・乗る前（預け荷物なし） | 保安検査の締切 ＋ 空港内移動 ＋ 安全余裕 | 航空会社の締切時刻は公式ページに基づいて `review-architecture.md` の検証表に記す。締切そのものではなく **締切＋利用者が安心できる余裕** を既定にする。数値は検証後に確定 [UNKNOWN：検証中] |
| 国内線・乗る前（預け荷物あり） | 上に手荷物の締切の差を加算 | 同上 |
| 国際線・乗る前 | 航空会社の推奨到着時刻（例 2〜3 時間）[UNKNOWN：検証中] | 同上 |
| 降りた後（預け荷物なし／あり） | 10〜15 分／25〜35 分 [GUESS] | 実測が無い。利用者が設定で変えられる |
| 飛行機→飛行機の最小乗継時間 | 空港ごとの MCT。無料で入手できる公的な一覧は **確認できていない** [UNKNOWN] | 無い場合は 国内→国内 60 分、国内↔国際 90〜120 分 [GUESS] を既定にし「目安」と表示 |

- 余裕は **利用者の条件（荷物・慣れ）** で変えられることを UI の前提にする。
- 便は「予約が要る・満席がありうる」ので、結果には「時刻の目安。空席・運賃は未確認」と必ず付ける（`architecture.md` 2.2 と同じ）。

### 7.3 飛行機データの形

- 便＝Trip（`mode=air`、便名、航空会社、運航日、機材は任意）。StopPoint＝空港ターミナル（出発・到着でターミナルが違う場合は別の StopPoint）。
- 入手先：`research-japan-data.md` は「国内線の時刻表のオープンデータは不明」としていたが、**ODPT のデータカタログに 全日空（国内線・国際線）と 日本航空（国内線）の「フライト時刻表」がある**。どちらも「公共交通オープンデータ基本ライセンス」[PROVEN：https://ckan.odpt.org/dataset/a_flightschedule-ana ・ https://ckan.odpt.org/dataset/a_flightschedule-jal（2026-10-19 閲覧）]。形は `odpt:FlightSchedule`（出発・到着空港、カレンダー、便ごとの 出発予定時刻・到着予定時刻・日付差・有効期間）[ARGUED：3.4 と同じ有志の OpenAPI 定義 `src/models/airplane.tsp`]。空港（`odpt:Airport`）とターミナル（`odpt:AirportTerminal`）の位置もある [ARGUED：同上]。
- したがって飛行機の Trip は ODPT の FlightSchedule から作る。基本ライセンスの本文（商用・再配布の条件）は `data-pipeline.md` の確認事項。登録完了までは **手入力の少数便** で動作確認する [ARGUED：データが無くても設計と検証は進められる。航空会社サイトの自動取得は行わない]。
- ODPT の FlightSchedule は「発着の予定時刻」であり、搭乗手続きの締切や最小乗継時間は含まない [ARGUED：属性一覧にそれらが無い]。余裕時間（7.2）は別に持つ。

## 8. 悪いデータへの耐性

### 8.1 取り込み時（データ側の守り。詳細は `data-pipeline.md`）
- 形式・参照整合性（存在しない stop_id を指す stop_time 等）、時刻の単調性（同じ Trip で到着が前の出発より早い）、速度の妥当性（駅間距離 ÷ 所要が 鉄道 160 km/h・バス 100 km/h を超える等 [GUESS]）、座標の妥当性（日本の範囲外、(0,0)）、重複 Trip。
- 違反した Trip／StopPoint は **隔離**（探索から除外、理由付きで記録）し、フィード全体は使う。隔離率が閾値（例 1% [GUESS]）を超えたらフィードごと前の版に留める。
- 前の版との差分（駅数・便数の急減、消えた路線）を検査し、急変時は人が確認するまで切り替えない（`architecture.md` 6 と同じ）。

### 8.2 探索時（エンジン側の守り）
- 待ち時間が負・乗り換え時間が負にならないことを表明（assert）し、違反は結果を捨てて記録する。
- 一定の上限（最大ラウンド数、最大徒歩、最大所要 例 36 時間 [GUESS]）で探索を打ち切る。
- 経路の各 Leg に「推定（乗り換え時間・徒歩）」「目安（頻度便・運賃）」の印を付けて返す（P3）。
- 時刻表の版が切り替わっても進行中の探索は古い版で完了させる（スナップショット不変、4.2 の 6）。

## 9. 検証計画

| 種類 | 内容 | 合格の目安 |
|---|---|---|
| **差分テスト（OTP）** | 同じ GTFS＋OSM を OTP 2 に入れ、無作為な (出発, 目的, 時刻) を多数（例 1,000 組 [GUESS]）投げ、最速到着・乗り換え最少の値を比較。OTP は照合の基準（`decisions.md` 1） | 到着時刻の一致率と差の分布を記録。**完全一致は目標にしない**（乗り換え時間の既定値・徒歩の扱いが違う）。差が出た組は分類（徒歩の差／乗換時間の差／本当の取りこぼし）し、取りこぼし 0 を目指す |
| **ゴールデン経路** | 人手で確かめた経路（例 首都圏 50 組 [GUESS]：渋谷→大手町、吉祥寺→横浜 等）。期待する到着時刻・乗り換え回数・経由路線を固定 | すべて一致。時刻表の版が変わったら人が更新する |
| **性質テスト（プロパティ）** | ①出発を遅らせても到着は早くならない（単調性）。②返す経路はすべて実行可能（各接続で 到着＋乗換時間≦出発）。③パレート集合の各要素は互いに支配されない。④最適経路の部分経路も最適（部分経路性、同じ乗り換え回数で）。⑤入力の順序（便の並び順）を変えても答えは同じ（決定性）。⑥逆向き探索と順向き探索の整合（「到着前」の答えの出発時刻で「出発後」を解くと同じ到着になる）。⑦直通の連結の有無で、連結前のデータでの「乗り換え 1 回」の答えと連結後の「乗り換え 0 回」の答えの時刻が一致 | 合成した小さな時刻表（数十駅）で無作為生成して数千回。違反 0 |
| **壊れたデータのテスト** | 参照切れ・時刻逆転・(0,0) 座標・重複便・空のフィード・巨大な frequencies を注入 | 落ちない。隔離の記録が出る。残りの経路は正しい |
| **性能** | 首都圏・全国規模で 95 パーセンタイルの応答時間とメモリ | 段階 1：都市内 100 ms 以下。段階 2：全国 2 秒以下（`architecture.md` 7 の基準を踏襲）[GUESS] |
| **再現性** | 時刻表の版 ID と問いから同じ答えが出る | 常に一致 |

- 差分テストの基準エンジンは OTP 2（LGPL-3.0 [PROVEN：`research-japan-data.md` の確認]）。本件は OTP を **実行して答えを比較するだけ** で、OTP のコードを組み込まないので、LGPL の義務（改変部分の公開）は生じない [ARGUED：LGPL の性質。法務の最終確認は `accounts-privacy.md` の質問一覧に含める]。

## 10. 計算量と規模の見積もり

### 10.1 理論（RAPTOR）
- 1 ラウンドの仕事量 ≦ 「そのラウンドで触れた全パターンの停留所数の合計」＋「触れた停留所から出る徒歩の本数」。最大 K ラウンドで **O(K × (Σ_パターン |停留所列| + |徒歩|))**。実際は改善のあった停留所を通るパターンだけ走査するので、ずっと少ない [PROVEN：Delling らの解析。各ラウンドで各パターンは高々 1 回走査される]。
- 範囲問い（rRAPTOR）は出発候補の数に比例して増えるが、後の出発から先に解いて枝刈りすると実用的 [PROVEN：同論文]。
- McRAPTOR は基準が増えるとラベル集合が膨らむ。3 基準（到着・乗換・運賃）までに留め、4 つ目以降は後処理で扱う [ARGUED]。

### 10.2 規模（首都圏の地下鉄＋私鉄、すべて [GUESS]。段階 1 で実測して置き換える）

| 項目 | 見積もり | 仮定 |
|---|---|---|
| 駅（束） | 1,000〜1,500 | 東京メトロ 約 180、都営 約 100、大手私鉄 ＋ 中小 で 800〜1,200 |
| 乗り場（StopPoint） | 3,000〜6,000 | 駅あたり 2〜4 番線 |
| パターン | 1,000〜3,000 | 路線 × 方向 × 種別 × 区間運転の組み合わせ |
| 便（Trip）／日 | 3〜6 万 | 路線あたり 1 日 数百〜千本 |
| 停車時刻（StopTime）／日 | 100〜200 万 | 便あたり 20〜40 駅 |
| メモリ（時刻表） | 数十 MB | StopTime 1 件 8 バイト（到着・出発 各 32 ビット）＋ 索引 |
| 1 問いの時間 | 数ミリ秒〜数十ミリ秒 | 5 ラウンド × 数百パターン × 30 駅 ≈ 10 万回の比較 |

### 10.3 規模（日本全国、鉄道＋バス＋フェリー、すべて [GUESS]）
| 項目 | 見積もり | 仮定 |
|---|---|---|
| 停留所 | 20〜30 万 | `architecture.md` 2.4 を踏襲。バス停の標柱が大半 |
| 便／日 | 50〜100 万 | バスが大半 |
| 停車時刻／日 | 2,000〜5,000 万 | 便あたり 30〜50 停留所 |
| メモリ | 1〜4 GB | 8 バイト × 5,000 万 ＝ 400 MB ＋ 索引・徒歩・7 日分のカレンダー |
| 1 問いの時間 | 都市内 数十 ms、全国横断 0.5〜2 秒 | 長距離は触れるパターンが多い。範囲問いはさらに増える |

- `architecture.md` 2.4 の「全国で 8〜32 GB」は OTP（Java・街路グラフ込み）を前提にした値で、自作の配列型 RAPTOR ならずっと小さい見込み [ARGUED：OTP はオブジェクト表現と OSM 街路グラフを持つ。数値は実測前の推測]。
- **飛行機**を同じエンジンに入れる追加コストは小さい（国内線は 1 日 数千便 [GUESS]、空港は約 100 [ARGUED：OurAirports で数えられる]）。

## 11. エンジンの境界（インタフェースの考え方）

実装言語・API の形は `src/` の担当に委ねるが、境界は次の 4 つに分ける [ARGUED：差し替えと検証のしやすさ]。
1. **Timetable Snapshot**：前処理済みの不変データ（Pattern・Trip・StopTime・Footpath・Service・AirBuffer・Provenance）。版 ID を持つ。
2. **Router**：Snapshot と問いを受け、Journey のパレート集合を返す純粋関数。外部 I/O なし。
3. **Street Access**：座標 ↔ 乗り場の徒歩接続を返す部品（OSM ベース。無ければ直線距離の代用）。
4. **Enricher**：Journey に名前・色・運賃の目安・来歴・表示用の印を付ける層。ここで「運賃不明」「推定」の文言を作る。
