# 経路探索の設計（自作・RAPTOR）

> **【レビュー注記・2026-10-19・中枢設計側から】** 本書の方針と `docs/core-design.md` の対応表は `core-design.md` 12 章にある。「次の段階 1：ODPT の CC BY のもの」について：東京メトロは CC BY ではなく基本ライセンス（商用可・再配布禁止・更新通知から 1 週間以内の反映）、都営は CC BY 4.0、大手私鉄 7 社と JR 東日本はチャレンジ 2026 限定のみ（`docs/data-pipeline.md` 1.1）。

印：「推」＝推測、「不明」＝未確認。

## 10 行の要約（非エンジニア向け）
1. 鉄道やバスの時刻表（GTFS という共通の形式）を読み込み、出発駅から目的駅までの経路を計算する部品を自作した。
2. 計算の方法は RAPTOR。「乗り換えなし」「1 回まで」「2 回まで」…と段階を増やしながら、各駅に一番早く着く時刻を求める。
3. そのため「速いが乗り換えが多い」「遅いが乗り換えが少ない」といった複数の案が自然に出る。
4. 平日・土休日・臨時ダイヤ（運行日の例外）、終電、夜 0 時をまたぐ便に対応した。
5. 同じ駅の別ホームや近くの駅への徒歩の乗り換えも扱う（データに無ければ直線距離から推定）。
6. 「何時までに着きたい」という指定もできる（簡易版）。
7. 飛行機やフェリーも「便の時刻表」として同じ仕組みに入れられる。搭乗手続きの余裕も設定できる。
8. 運賃はまだ計算しない。後で足すための差し込み口だけ用意した。
9. 試験：答えの分かる小さな路線網、性質の試験、駅 3,000・便 50,000 の大きな合成網での速さの計測（1 回の探索は中央値 約 8 ミリ秒・この環境での参考値）。
10. 首都圏の実データでの確認と、OpenTripPlanner（比較の基準）との照合はまだ（データの登録待ち）。照合の入力・比較の道具は用意した。

## 全体の流れ
```
GTFS のフォルダ ─(src/gtfs/load.ts：1 行ずつ読む)→ GtfsFeed（型付き配列）
   └─(src/network.ts)→ Network：経路パターン・停留所→パターン・徒歩のつながり
        └─ day(運行日)：前日・当日・翌日に動く便を、問い合わせ日の時刻に直して並べる（日付ごとに保持）
             └─(src/raptor.ts)→ Router.depart / Router.arriveBy → Journey[]（区間つき）
                  └─ FareCalculator（差し込み口・いまは何もしない）
```

## データの読み込み（src/gtfs/）
- CSV は自作のストリーム読み込み（1 MB ずつ）。引用符・引用符の中の改行・BOM・CRLF に対応。
- stop_times は型付き配列（Int32Array 等）に詰めて、(便, stop_sequence) で並べ替える。100 万行で約 4 秒・ヒープ約 20 MB（下の計測）。
  文字列は停留所・便・路線の ID と名前だけを持つ。
- 時刻の無い停車（時刻点でない停留所）は前後の時刻点から直線で補う。始発か終着に時刻が無い便は除外。
- 読むファイル：agency（時間帯）・stops・routes・trips・stop_times・calendar・calendar_dates・transfers。
  frequencies は未対応（警告を出して無視）。fare_*・shapes・translations・pathways は読まない。

## 路線網の組み直し（src/network.ts）
- **経路パターン**：同じ路線・同じ停車駅の並び・同じ乗降条件（pickup_type / drop_off_type＝1 の位置）の便の集まり。
  RAPTOR は「1 つのパターンの中で便が追い越さない」ことを前提にするので、追い越す便（各停と急行が同じ停車駅の並びを持つ場合など）は別のパターンに分ける。
- **運行日**：calendar（曜日・期間）と calendar_dates（1＝追加・2＝削除。こちらを優先）。
  問い合わせ日 D について、D−1・D・D+1 の便を「D の 0 時からの秒」に直して並べる。
  D−1 の便は 24 時を超えるものだけを入れる（夜中の問い合わせで前日の深夜便に乗れる）。D+1 は終電後に翌朝の始発を出すため。
- **徒歩のつながり**（優先順：transfers.txt ＞ 同じ駅のホーム間 ＞ 直線距離）
  - transfers.txt：type 2 は min_transfer_time、type 0・1 は距離からの推定、type 3（不可）は取り除く。from=to は同じ停留所での乗り換え時間。駅 ID が書かれていれば子のホームに広げる。type 4・5（便どうしの直通）は未対応。
  - 同じ駅（parent_station が同じ）のホーム間：既定 120 秒（推）か、距離からの推定の長い方。
  - 直線距離：transfers.txt が無いときだけ（既定）。400 m 以内、距離×1.3（回り道・推）÷1.2 m/秒（推）。格子で近いものだけ比べる。
  - 徒歩は「出発直後」と「降車直後」に 1 回だけ（徒歩をつなげて歩き続けることはしない）。RAPTOR の標準の扱い。transfers は推移的に閉じていることが望ましい（不足すると遠回りの徒歩を見落とす）。

## 探索（src/raptor.ts）
- ラウンド k（k＝乗車回数）ごとに、印の付いた停留所を通るパターンだけを、最も手前の位置から 1 回なめる。
  - 乗れる最も早い便は、その位置の出発時刻の列を二分探索（便は追い越さないので列は並んでいる）。
  - 着いた時刻が、その停留所の過去の最良（全ラウンド）と目的地の最良より早いときだけ更新（標準の枝刈り）。
  - 更新した停留所から、同じ停留所の乗り換え時間と徒歩を足して、次のラウンドで乗れる時刻を作る。
- 目的地の最良の到着がラウンド k で改善したら、その経路を候補に加える → 候補は「乗り換えが増えるほど到着が真に早い」パレート最適の並び。
- 乗り換え回数の上限（既定 6）。手段の除外（modes）。手段ごとの乗る前の余裕（ModeProfile.boardSlack。既定：飛行機 30 分・フェリー 10 分＝推）。
- 経路の復元：ラウンドごとに「どのパターン・どの便・どこで乗ってどこで降りたか」「どこから歩いたか」を記録し、目的地から逆にたどる。
  区間ごとに路線名・行き先・乗車駅・降車駅・時刻（現地時刻の ISO）・途中の停車数を返す。
- **到着時刻の指定（簡易版）**：乗り換え回数の上限 k＝0…K のそれぞれで、期限に間に合う最も遅い出発時刻を分単位の二分探索で求め、
  「出発が遅い × 乗り換えが少ない」でパレート最適なものを返す。正しさは「出発を遅らせても到着は早くならない」（FIFO）性質に依る。
  探索回数は (K+1)×約 10 回。逆向きの RAPTOR（到着から逆にたどる）にすれば 1 回で済む（次の段階）。

### 計算量
- 1 回の探索：O(K × (通るパターンの停車の数の合計 ＋ 徒歩のつながりの数) ＋ 二分探索の log)。全停留所の配列をラウンドごとに作るので O(K × 停留所数) のメモリと初期化もかかる。
- 前処理：読み込み O(stop_times の行数 × log)（並べ替え）、運行日の時刻表 O(その日に動く便の停車数 × 3)。

### 正しさの確かめ方
- 合成の小さな網：最速の経路と区間（徒歩乗り換えの選択）、乗り換え上限、同じ駅の別ホームの乗り換え時間、終電と翌朝、日またぎ、運行日の例外、乗降不可の停車、直線距離の徒歩、時刻の補間と追い越し、飛行機の余裕と手段の除外、到着時刻の指定。
- 性質：別の方式（接続走査＝CSA の素朴な実装）と最早到着が一致（150 問）、出発を遅らせても到着は早くならない、乗り換え上限が効く・上限を上げても遅くならない、パレートの並び、区間の時刻と駅のつながり、到着指定の結果が期限内で 1 分遅い出発では間に合わない。

## 日本の癖への対応
| 癖 | 対応 | 状態 |
|---|---|---|
| 日本語の名前 | UTF-8 のまま扱う。BOM 付きでも読める | 済 |
| 同じ駅の複数ホーム（parent_station） | 駅 ID の指定を子のホームに広げる。ホーム間に既定の乗り換え時間 | 済（既定の 120 秒は推） |
| 24 時を超える時刻（25:10 など） | 秒で持ち、前日の便として当日 0 時台に乗れる | 済 |
| 臨時ダイヤ（calendar_dates） | 追加・削除に対応 | 済 |
| 降車専用・乗車専用の停車（GTFS-JP のバスで多い） | pickup_type / drop_off_type＝1 を守る | 済 |
| 直通運転（他社線への乗り入れ） | 同じ便のまま走るデータなら 1 本の乗車。便が分かれていて block_id や transfers の type 4 でつながる場合は未対応 | 未（不明：首都圏のデータの作り方による） |
| 大きな駅の構内の歩行時間 | transfers.txt があれば使う。pathways.txt は未対応 | 一部 |
| 翻訳（translations.txt・英語名） | 読まない | 未 |
| 運賃（IC と切符・乗継割引など） | 差し込み口だけ | 未（決定 #3） |

## 既知の限界
- 1 つのパターンの中の便は追い越さない前提。24 時間を超える便が日をまたいで並ぶと崩れうる（警告を出す）。
- 出発時刻の幅を持った探索（rRAPTOR＝ある時間帯の全ての良い出発）は未対応。「早く出ても到着が同じなら遅く出る」案の整理もしない（先頭が徒歩の場合だけ出発を詰める）。
- 同じ到着・同じ乗り換え回数の案が複数あっても 1 つしか返さない（どれを返すかはデータの並びによる）。
- 徒歩の速さ・回り道の係数・ホーム間の既定時間は仮の値（推）。
- GTFS の時刻の基準（正午の 12 時間前）を 0 時として扱う。夏時間の無い日本では差は出ないが、海外では要対応。
- 地点（住所・緯度経度）からの探索は未対応。最寄りの停留所を選ぶ部品が別に要る。
- zip の直接読み込みは未対応（展開したフォルダを渡す）。

## 次の段階（案）
1. 首都圏の鉄道の実データ（ODPT の CC BY のもの）で動かし、OpenTripPlanner と同じ入力（`validation/` の形式）で照合する。
2. 逆向きの RAPTOR（到着時刻の指定を 1 回で）と rRAPTOR（時間帯の探索）。
3. 直通運転（block_id・transfers の type 4/5）と pathways.txt。
4. 地点からの探索（最寄りの停留所への徒歩）。
5. 飛行機の層：空港ごとの搭乗の余裕、空港⇔市街の地上経路との接続（`docs/architecture.md` 2 章）。
6. 運賃の差し込み（目安の表示から。FareCalculator を実装）。
7. 性能：配列の使い回し（ラウンドごとの確保をやめる）、運行日の時刻表の上限管理、複数の CPU での並列。

## 照合の土台（validation/・src/validation.ts）
- 入力：`gyrotraffic-cases/1`（GTFS の説明・時間帯・問い合わせの一覧＝出発・到着・出発時刻か到着時刻・乗り換え上限・任意の期待値）。
- 出力：`gyrotraffic-results/1`（問い合わせごとの案：出発・到着の現地時刻、乗り換え回数、乗車区間の路線・駅・時刻）。
- `gyrotraffic run-cases` で自分の結果を作り、OTP の GraphQL（plan）の応答は `otpPlanToItineraries` で同じ形に直す（雛形。実物の OTP の応答では未確認＝不明）。
- `gyrotraffic compare a.json b.json`：最も早い到着の差が許容（既定 300 秒）以内で、最少の乗り換え回数が同じなら一致。
- OTP は入れていない・走らせていない。
