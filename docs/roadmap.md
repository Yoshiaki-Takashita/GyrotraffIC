# 段階計画（ロードマップ）　第 1 版・2026-10-19

> 印の意味：**[PROVEN]**＝一次資料か既決事項で確認済み。**[ARGUED]**＝根拠を示した推論。**[GUESS]**＝推測。**[UNKNOWN]**＝分かっていない。
> 前提：`docs/decisions.md`（自作 RAPTOR、首都圏の地下鉄・私鉄から、運賃は後、履歴は端末のみ、試作中の有料データは 0 円）。

## 要約（非エンジニア向け・10 行）
1. 最初に出すもの（最小の一歩）は「**東京の地下鉄（東京メトロ・都営）と、通常利用できる数社（つくばエクスプレス・りんかい線・横浜市営・多摩モノレール）だけ、駅から駅、出発時刻を指定して、最速と乗り換え最少の 2 案を出すウェブ 1 画面**」。JR と大手私鉄を含まないことを画面に正直に書く。
2. 段階は 0〜6 の 7 つ。各段階に **数で測れる完成条件** を付けた。
3. 今は ODPT のデータが無いので、段階 0 は「作った時刻表（合成データ）と、使えるバスの公開データ」でエンジンと検査の仕組みを先に作る。
4. 飛行機は段階 3。ただし **羽田・成田への鉄道（京急・東京モノレール・京成）のデータが通常利用できない** ので、空港アクセスは都営浅草線の範囲・バス・手入力で始める。
5. **JR 東日本と大手私鉄 7 社の ODPT データは「チャレンジ 2026 限定」だけ**（2027-03-12 失効、応募と無料機能の公開が条件、JR 東日本は競合禁止条項あり）。全国展開（段階 5）どころか首都圏の仕上げも、この入手方法の決定（D7）に掛かる。これが最大の不確定要素。
6. お金が掛かる判断（JR の有料 API、地図の有料枠）は、段階 1 の実測値を見てから決める。
7. 最大の危険は「データが手に入らない」「乗り場の精度が出ない」「法務の確認が遅れる」の 3 つ。それぞれに前倒しの対策を書いた。
8. 所有者にしか決められないことは 7 つ（8 章）。所有者の「任せる」により、推奨どおりに決定済み（`decisions.md`）。
9. 日程は書かない。段階は「条件を満たしたら次へ」で進める（所有者の作業時間が読めないため）。
10. 各段階の終わりに `decisions.md` に決定を追記し、この文書を改訂する。

## 1. 最小の一歩（smallest shippable slice）

| 項目 | 内容 |
|---|---|
| 範囲 | 首都圏の鉄道のうち **通常利用できるライセンスのデータ** だけ：東京メトロ（基本ライセンス）、都営（CC BY 4.0）、つくばエクスプレス・りんかい線・横浜市営地下鉄・多摩モノレール（基本ライセンス）[PROVEN：`data-pipeline.md` 1.1]。JR・大手私鉄・バス・飛行機は含まない |

| 出力 | 最速・乗り換え最少の 2 案。各案に 路線名・乗車駅・降車駅・時刻・乗り換え回数。出典とライセンスの表示 |

## 4. 段階 0 の進め方（今、ODPT が無い間にできること）

1. **合成時刻表** を作る（0-2 の要件を満たす小さな GTFS）。ここに日本特有の罠（直通・24 時超え・祝日・同名の別駅）を意図的に入れる。
2. **GTFS-JP の公開バスフィード** を 1 つ選ぶ。選ぶ基準：ライセンスが CC BY 4.0 か CC0 と **ページ上で明示** されていること（`data-pipeline.md`）。これで差分テストと取り込みの検査を本物のデータで回す。
3. OTP 2 を照合用に立てる（Docker）。LGPL のため組み込まず、実行して答えを比べるだけ（`core-design.md` 9 章）。
4. 来歴・ライセンスの枠組みを最初から入れる（後から足すのは全データの作り直しになる）。
5. 空港・便の **手入力の試験データ** を作る（段階 3 の先行）。

### 4.1 次にやること（2026-10-19 更新・`core-alignment.md` の差から）
1. **実データの取り込み**：ODPT の登録（確認メール未着）を待つ間は、公開 GTFS-JP（CC BY）で feed_info.txt の版・ライセンスを読み、区間ごとの来歴（0-6）を付ける。ODPT が来たら都営（CC BY 4.0）から。祝日の展開と「特別ダイヤ未反映」の表示、frequencies.txt の展開も取り込み側で。
2. **始発・終電の探索**：実装済み（2026-10-19、`src/first-last.ts`・`first-last.md` 0 章）。残り：逆向き RAPTOR による到着時刻指定の簡易版の置き換え（今は併存）、祝日の展開、運行日の境界（03:00 は仮）の確認、画面側の対応（担当に依頼）。
3. **運賃**：3 値の型（`FareValue`）と合成は済。次は運賃データ（GTFS Fares v2 など）から Leg ごとの値を作る FareCalculator と、Router からの受け渡し。「安い」案は Known だけで並べる。
4. そのあと：徒歩の推移閉包（上限つき）、直通（block_id・transfers type 4/5）、pathways.txt。
5. 画面との接続：`src/ui-adapter/` が static-provider と同じ形で中枢の出力を返す。画面側での切り替え（`GT_CONFIG.provider`）は画面の担当に依頼する。
