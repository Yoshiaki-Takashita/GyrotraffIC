# データ取り込み（データパイプライン）とライセンスの守り　第 1 版・2026-10-19

> 印の意味：**[PROVEN]**＝一次資料で確認済み（URL を付記）。**[ARGUED]**＝根拠を示した推論。**[GUESS]**＝推測。**[UNKNOWN]**＝分かっていない。
> ODPT の規約・ライセンスは **日本語版が正文**（英語版は参考）[PROVEN：基本ライセンス第 18 条 2 項、センター利用規約第 16 条 2 項]。本書で引用した英語版の条文は、登録後に日本語の正文で読み直す。

## 要約（非エンジニア向け・10 行）
1. データは「取ってくる → そのまま保管 → 共通の形に直す → 検査 → つなぐ（駅の束など）→ 版を付けて固める → 前の版と比べる → 切り替える」の順に流す。各段の結果は捨てず、いつでも前の版に戻せる。
2. 表示するすべての事実（時刻・位置・名前・運賃）に「どのデータ源の・どの版の・どのライセンスか」を付ける。これを **来歴（プロヴェナンス）** と呼ぶ。
3. ODPT の「基本ライセンス」は **商用利用は可**、ただし **データそのもの（複製・復元できる加工物を含む）を第三者に配ることは禁止**、データ更新の通知から **1 週間以内に反映** が義務、**出典の表示** と **「正確さは保証しない」の告知** と **連絡先メール** が必要 [PROVEN：英語版の条文]。
4. 東京メトロは基本ライセンス、都営は CC BY 4.0。`decisions.md` の「CC BY のデータ」という前提は **東京メトロには当てはまらない**。
5. **JR 東日本と大手私鉄 7 社（小田急・東急・京王・西武・東武・京急・相鉄）の ODPT データは「チャレンジ 2026 限定」だけ**で、通常の利用はできない（許諾は 2027-03-12 まで、応募と無料機能の公開が条件）。京成・東京モノレールは ODPT に無い。通常の利用で使える首都圏の鉄道は、東京メトロ・都営・つくばエクスプレス・りんかい線・横浜市営・多摩モノレール（ゆりかもめは時刻表なし）に限られる。
6. OpenStreetMap は ODbL：出典表示が必須で、OSM を改変・結合して作ったデータベースを公開利用するなら同じ ODbL で公開する義務がありうる。自前の実測データは OSM 由来と **別の層** に置く。
7. 全日空・日本航空のフライト時刻表が ODPT にある（基本ライセンス）。飛行機の便はここから取る。
8. 祝日は内閣府の「国民の祝日」CSV（1955〜2027 年）で展開する。
9. データが欠けている時は「未収録」と正直に出し、古い時は「○月○日の時刻表」と版の日付を出す。黙って前の版を使い続けない。
10. 端末にオフライン用の時刻表を置く案（`architecture.md` 6 章）は、基本ライセンスの再配布禁止に **抵触する可能性** がある。弁護士への質問に加えた。

**設計への帰結** [ARGUED]
1. 本サービスが外に出すのは **計算結果（経路）と画面** であり、時刻表そのものや「元に戻せる加工物」は出さない。公開 API を作る時は、生データや全列車の時刻表を返す形にしない（第 8 条 4 項 1 号）。
2. **端末へのオフライン時刻表の配布**（`architecture.md` 6 章「段階 5 以降の検討」）は、基本ライセンスデータの複製を利用者の端末に送ることになり、第 8 条に当たる可能性がある。やるなら書面の承諾が要る [UNKNOWN → `accounts-privacy.md` の質問に Q13 として追加]。CC BY のデータだけなら可能。
3. 更新通知を見落とさないため、ODPT の更新を **毎日** 確認し、通知から 1 週間以内に新しい版へ切り替える（3 章）。切り替えに失敗したら警告を出す。
4. アプリの「データについて」画面に、出典表示・免責・連絡先メールを常設する。
5. 契約終了時にデータを消せるよう、ODPT 由来のレコードは来歴で一括検索できるようにしておく（5 章）。

### 1.3 チャレンジ限定ライセンスの要点と「例外」の選択肢

- 利用目的：成果物の作成・公開と、チャレンジへの応募。「限定ライセンスデータを利用する目的が本チャレンジに応募すること以外にもあると…判断した場合、…利用することを終了させる…」[PROVEN：第 4 条 1]。
- 企業のサービスでも使えるが、「本チャレンジへの応募を行うこと、及び、本チャレンジの期間中誰でも無償で利用できる機能を公開することを必須」[PROVEN：第 4 条 7]。
- 再配布禁止は基本ライセンスと同じ [PROVEN：第 8 条 4 (1)]。応募規約では「本データを、有償または無償にかかわらず、第三者に提供してはならない」。
- **期限**：許諾は **2027-03-12 に終了**（第 13 条 2）。終了時はデータを削除（第 13 条 3）。チャレンジ 2026 の応募期間は 2026-10-01〜2027-01-11 [PROVEN：JS バンドル内の記載]。
- JR 東日本の個別条件（2026-08-06）：JR 東日本のデータから作った成果物で **JR 東日本のサービスと競合するサービスを作らない**、知的財産を JR 東日本に主張しない（契約終了後も存続）[PROVEN：個別条件 第 1 条]。
- **帰結** [ARGUED]：JR 東日本と大手私鉄 7 社のデータを使う **唯一の無料の道** は、チャレンジ 2026 に応募し、無料機能を公開することだが、2027-03-12 で失効し、JR 東日本の「競合禁止」条項は経路案内アプリに重くのしかかる可能性がある。通常の運用に組み込む前提にはできない。所有者の決定事項（`roadmap.md` D7）。

## 2. 取り込みの流れ

```
[1 取得 fetch] → [2 原本保管 archive] → [3 解釈 parse] → [4 正規化 normalize]
→ [5 検査 validate] → [6 連結 link] → [7 版の確定 snapshot] → [8 前版との比較 diff]
→ [9 切り替え publish] → [10 配信 serve]
```

| 段 | 入力 → 出力 | 要点 |
|---|---|---|
| 1 取得 | 各データ源の URL・API → 生ファイル | データ源ごとの「取得部品（アダプタ）」。ETag／Last-Modified／`dc:date`／ファイルのハッシュで変化を検知。ODPT は API キー、GTFS-JP は zip、OSM は地域抜粋（PBF）、祝日は CSV |
| 2 原本保管 | 生ファイル → 不変の原本（ハッシュ名、取得日時、URL、HTTP ヘッダ、ライセンス ID） | 取得したものは **そのまま** 残す。再処理と監査のため。保管期間は 1 年 [GUESS]。ODPT のデータは契約終了時に削除できるよう印を付ける |
| 3 解釈 | 原本 → データ源固有のレコード | GTFS は CSV の表、ODPT は JSON-LD。ここでは意味を変えない |
| 4 正規化 | 固有レコード → 共通モデル（`core-design.md` 3 章） | ID の付け替え（`源:元ID`）、時刻の秒化、`frequencies` の展開、運行日の日付展開（祝日 CSV）、座標の WGS84 確認、文字の正規化（全角・半角・異体字）。**各レコードに来歴を付ける**（5 章） |
| 5 検査 | 共通モデル → 合格レコード＋隔離レコード＋報告 | 4 章の検査項目。隔離は理由付き |
| 6 連結 | 合格レコード → 駅の束、乗り場の等価、出入口の対応、直通の連結、徒歩グラフ | 複数データ源にまたがる処理。根拠と確信度を記録（`platform-precision.md` 3 章） |
| 7 版の確定 | 連結済み → スナップショット（版 ID、含まれるデータ源と各版、ライセンス一覧、統計） | エンジンの前処理（`core-design.md` 4.2）もここで行う。不変 |
| 8 比較 | 新版 vs 現行版 → 差分報告 | 駅数・便数・路線数の増減、消えた事業者、ゴールデン経路の答えの変化。閾値超えは人の承認待ち |
| 9 切り替え | 承認 → 現行版の更新 | エンジンを新版で立ち上げ、動作確認後に切り替え。前版は即時に戻せる状態で保持（最低 3 版 [GUESS]） |
| 10 配信 | 現行版 → 探索・表示 | 結果に版 ID と来歴を付けて返す |

- 失敗時：どの段で失敗しても **現行版はそのまま**。失敗は記録し、1.2 の「1 週間」の義務に関わるものは警告を上げる。
- 再現性：原本と部品のバージョンが同じなら同じスナップショットができる（決定的）。

## 3. 版と更新の頻度

### 3.1 版（バージョン）の付け方
- **データ源の版**：取得したファイルのハッシュ＋取得日時（例 `odpt-tokyometro-traintimetable@2026-10-19T03:00Z#ab12…`）。ODPT の `dc:date`（データ生成日時）、GTFS の `feed_info.txt`（`feed_version`・有効期間）があれば併記。
- **スナップショットの版**：`YYYYMMDD-N`（同日複数回に対応）＋含まれるデータ源の版の一覧。探索結果はこの ID を返す。
- **履歴**：どの日にどの版が現行だったかを記録し、「あの日に出した答え」を再現できるようにする（不具合調査・ゴールデン更新のため）。

### 3.2 更新の頻度（データ源ごと）
| データ源 | 確認 | 再構築 | 根拠 |
|---|---|---|---|
| ODPT 静的（駅・路線・列車時刻表・運賃） | **毎日**（更新通知・`dc:date`・ハッシュ） | 変化があった日 | 「通知から 1 週間以内」の義務 [PROVEN：ガイドライン 2.2.2]。週 1 回の確認では期限を外す危険がある [ARGUED] |
| ODPT フライト時刻表 | 毎日 | 変化があった日 | `odpt:isValidFrom`／`isValidTo` で便ごとの有効期間がある [ARGUED：`core-design.md` 7.3] |
| ODPT 動的（運行情報・リアルタイム） | 当面使わない | — | 使う時は `odpt:frequency`・`dct:valid` に従う [PROVEN] |
| GTFS-JP の各フィード | 週 1 回。ダイヤ改正（3 月・10 月に多い [GUESS]）の前後は毎日 | 変化があった週 | `feed_info` の有効期間の終わりが近いフィードを警告 |
| OSM 地域抜粋 | 月 1 回 | 月 1 回 | 出入口・ホームの変化は遅い [GUESS]。主要駅の実測（`platform-precision.md` 8 章）は年 1 回 |
| 祝日 CSV | 年 1 回（翌年分の公表後） | 年 1 回 | 2027 年まで収録 [PROVEN] |
| OurAirports | 月 1 回 | — | 変化は少ない |

## 4. 検査（validate）の項目

| 区分 | 検査 | 違反時 |
|---|---|---|
| 形式 | 必須列の有無、文字コード、数値・時刻の書式 | ファイル単位で失敗 → 現行版を維持 |
| 参照 | `stop_times` の `trip_id`／`stop_id`、`trips` の `route_id`／`service_id`、ODPT の ID 参照（`odpt:station`、`previousTrainTimetable` 等）の存在 | 参照切れのレコードを隔離 |
| 時刻 | 同じ便で到着 ≦ 出発、次の停留所の時刻 ≧ 前の出発。24 時超えは許す | 便を隔離 |
| 速度 | 停留所間の直線距離 ÷ 所要が 鉄道 160 km/h、バス 100 km/h、フェリー 60 km/h、飛行機 1,000 km/h を超える [GUESS] | 便に「要確認」の印（隔離はしない。長い駅間で誤検知しうる） |
| 座標 | 日本の範囲（緯度 20〜46、経度 122〜154 [ARGUED：国土の範囲]）、(0,0)、重複する停留所の座標 | 停留所を隔離（段階 D として名前だけ残す案も可） |
| 運行日 | `calendar`・`calendar_dates` の整合、有効期間の終わりが 14 日以内 [GUESS] | 期限切れ間近を警告 |
| 重複 | 同じ Trip の二重取り込み、同じ停留所 ID の二重定義 | 後勝ちにせず隔離 |
| 統計 | 事業者ごとの駅数・便数・路線数と前版の差（例 ±20% [GUESS]） | 人の承認待ち |
| ゴールデン | `core-design.md` 9 章のゴールデン経路の答えが変わっていないか | 変化があれば人の確認 |
| ライセンス | すべてのレコードにライセンス ID があるか。「使わない」ライセンス（チャレンジ限定）が混ざっていないか | **切り替えを止める** |

- 隔離率がフィードの 1% [GUESS] を超えたらフィードごと前の版に留める。

## 5. 来歴（プロヴェナンス）

### 5.1 目的
画面に出る **どの事実** についても「出どころ・版・ライセンス・加工」を答えられること。これは ①ライセンスの出典表示、②契約終了時の削除、③不具合の原因追跡、④差分テストの差の分類、の 4 つに同時に必要 [ARGUED]。

### 5.2 構造
```
Source        { source_id, name, publisher, url, license_id, contact, notes }
License       { license_id, name, url, attribution_text, redistribution: allowed|forbidden|conditional,
                share_alike: bool, update_obligation: "1w"|null, notes }
SourceVersion { source_id, version_id, fetched_at, content_hash, http_etag, upstream_date, valid_from, valid_to }
Record        { record_id, kind, ..., prov: ProvRef }
ProvRef       { source_id, version_id, license_id, upstream_id, transform: [step...] }
Derived       { record_id, inputs: [ProvRef...], method, confidence, prov: ProvRef }
```
- 単一のデータ源から来たレコードは `ProvRef` を 1 つ持つ。
- 複数から作ったもの（駅の束、徒歩グラフ、推定の乗り換え時間）は `Derived` として **入力の来歴をすべて** 持つ。ODbL の判定（OSM が入力に入っているか）はここで機械的にできる。
- 探索結果の各 Leg は、乗った便・乗り場・出入口・徒歩の `ProvRef` を参照する。画面はそこから **使ったデータ源の集合** を作り、出典表示に並べる。

### 5.3 表示の規則
- 結果画面の末尾に「この経路に使ったデータ」：データ源の名前と版の日付、ライセンス名、必要な出典文（ODPT は 1.2 の文言、OSM は「© OpenStreetMap contributors」＋ ODbL、CC BY は提供者名）。
- 「データについて」画面に全データ源の一覧・免責・連絡先メール（ODPT ガイドライン 3.1）。
- 推定した値（乗り換え時間・位置の段階 C／D）には「推定」の印（`core-design.md` P3）。

## 6. 欠けている・古い時の扱い

| 状況 | 検知 | 扱い |
|---|---|---|
| 事業者がデータを出していない（JR 等） | 「未収録事業者」の一覧を手で管理 | 画面に **「JR 線は含みません」** 等を常に表示。検索で未収録の駅名が入力されたら「このアプリは○○線を扱っていません」と返す（答えを出さない方が、遠回りの答えを出すより良い）[ARGUED] |
| フィードの有効期間が切れた | `feed_info`／`isValidTo`／`calendar` の終わり | 期限後は **その事業者の便を出さず**「時刻表の期限切れ（○月○日）」を表示。更新が来るまで前版は使わない [ARGUED：古い時刻表で案内する害の方が大きい]。ただし有効期間が無いデータ（ODPT の一部）は「最終更新日」を表示して使い続ける |
| 更新に失敗した（取得できない・検査で落ちた） | 2 章の失敗記録 | 現行版を維持し、画面に「最終更新 ○月○日」。ODPT の 1 週間の期限が迫ったら運用者に警告。期限を過ぎたら **その事業者の表示を止める**（ライセンス上の義務）[ARGUED：第 4 条 2 項 4 号の帰結] |
| 一部のレコードが隔離された | 検査報告 | 隔離した便・停留所を除いて配信。隔離の多い路線には「一部の便を表示できません」 |
| 特別ダイヤ（年末年始など）が未反映 | データに `calendar_dates` の該当が無い | 「特別ダイヤ未反映の場合あり」（`core-design.md` 6 章） |
| 乗り場位置が無い | `platform-precision.md` 7 章 | 段階 D の表示と外部地図へのリンク |
| 運賃が無い | `core-design.md` 4.4 | 「運賃不明」 |
| ODPT が提供を終了した | 通知 | 該当データを削除し（第 13 条 3 項）、画面から外す。来歴で一括検索できる |

## 7. 運用の最小構成（段階 1）

- 取り込みは 1 台のバッチ（毎日 1 回、夜間）。原本保管はオブジェクトストレージか単なるディスク。
- 承認待ちは「報告をメールで受け取り、コマンド 1 つで切り替え」で十分 [ARGUED：個人開発の規模]。
- 監視：最終成功日時、各データ源の最終更新日、1 週間期限までの残り日数、隔離率。
